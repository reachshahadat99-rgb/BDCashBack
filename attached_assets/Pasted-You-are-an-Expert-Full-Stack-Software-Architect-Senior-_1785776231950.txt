## STEP 0 — Mandatory First Step: Audit Before Any Code Change

Before writing or editing a single file, do the following and report back:

1. **Scan the actual project structure** (routes, Prisma schema, components, API handlers, lib/services).
2. **Build a Gap Report** structured like this, per module from the spec:

   | Module | Status | What Exists | What's Missing/Broken | Risk if Skipped |
   |---|---|---|---|---|
   | Wallet | Partial | balance, add money | pending vs available cashback not separated | Cashback logic breaks |

3. **Do not assume anything works** just because a file with the right name exists — verify the logic matches the spec (e.g., a "Wallet" page existing is not the same as pending/available cashback being correctly split and cashback-release-on-delivery being implemented).
4. Present the Gap Report and a proposed fix order **before** touching code, unless explicitly told to skip this and go straight to fixes.

## STEP 1 — Fix Order Rules

* Fix in dependency order: Database schema → Auth/RBAC → Core business logic (wallet, cashback, orders) → Feature modules (coupons, deals, group buy, gift cards, watch & earn) → Admin/Merchant panels → Polish/UI/Performance.
* Never modify the Prisma schema without generating a migration and stating what data, if any, is at risk.
* Never change an API's response shape or an existing route's contract without flagging it as a **breaking change** and listing every place in the codebase that calls it.
* One module fully fixed and verified before moving to the next — same discipline as original build rules below.

---

## STEP 2 — After Every Fix, Verify

* `npm run build` succeeds
* TypeScript has zero errors (no `any` used to silence a real type mismatch)
* `npx prisma validate` / migration applies cleanly
* Affected API endpoints tested (happy path + at least one failure case: invalid input, unauthorized, payment failure, fraud/edge case where relevant)
* Affected UI is responsive and functions in both dark and light mode
* No console errors/warnings introduced

Report verification results after each fix, not just at the end.

---

## STEP 3 — Regression Safety

* Before editing shared code (auth, wallet service, cashback engine, payment webhook handlers), list every feature that depends on it.
* After editing, confirm each dependent feature still works — do not just confirm the one feature you were fixing.
* If a fix requires a breaking change, propose a migration path instead of a silent break (e.g., versioned API route, feature flag, backward-compatible field).
