Part 4 — Merchant-Parity Admin Access (NEW backend + frontend)

Goal: From the admin panel, an admin can open any merchant's store and perform the same actions that merchant could perform in /merchant — manage products, view/update orders, manage that merchant's coupons/deals/group buy campaigns — without needing to log in as that merchant.

This is for support, moderation, and emergency intervention (e.g., a merchant is unreachable and an order needs updating, or a listing needs correcting after a policy violation).

Backend (new — the key gap)

The current merchant routes (/merchant/store, /merchant/products, /merchant/orders, etc.) are scoped to the authenticated merchant's own merchant_stores record. Add admin-scoped equivalents that take an explicit store ID, e.g.:

GET /admin/stores/:storeId/products / POST / PATCH /:id / DELETE /:id
GET /admin/stores/:storeId/orders / PATCH /:id/status
GET /admin/stores/:storeId/coupons (admin can approve/edit directly, bypassing the merchant-submits-admin-approves flow when acting on their behalf)
GET /admin/stores/:storeId/summary (same dashboard data the merchant sees for their own store)

Every one of these must write to audit_logs with the admin's ID and the store ID acted on — this is admin acting on another party's data, so the audit trail matters even more here than elsewhere.

Do not implement this as "admin logs in as merchant" (session swapping) — implement it as admin-scoped routes with their own permission check (requireAdmin + explicit store ID), so the action is clearly attributable to the admin, not disguised as the merchant's own action.

Frontend (new)
From the Merchants tab, each merchant row gets a "Manage Store" action that opens a read/write view mirroring the Merchant Dashboard's own UI (Products, Orders, Coupons, Deals, Group Buy, Summary) but scoped to that store, reusing the merchant panel's components where possible with the storeId passed in as a prop instead of derived from the logged-in user.
Clearly label this view (e.g., a banner: "You are managing [Store Name] as Admin — actions are logged") so it's never ambiguous that the admin is acting on someone else's store.
